## Notes / known limitations

- **Queue-full/drop policy is not reachable through normal TCP protocol
  usage** while the server is healthy and running, because its `epoll`
  loop drains `/dev/vmonitor` as soon as `poll()` reports it readable
  (immediately after every `write()`, since the driver wakes the wait
  queue). This is intentional, correct behavior -- a real-time relay
  should not let its own buffer fill up under normal operation.
- The drop policy **is** reachable, and was verified end-to-end, in the
  realistic scenario where the server is not running (e.g. crashed) while
  the timer is still active (`STOP` was never called) -- see scenario 25.
  `tests/devctl.c` was written specifically for this: a minimal tool that
  talks to `/dev/vmonitor` directly via `ioctl`, independent of the server,
  useful for exactly this kind of low-level inspection.
- No bugs were found during Day 5 testing; all scenarios behaved as
  expected once correctly understood (see the discussion around
  scenario 21/25 above for the one case that needed a second look).
